# Shared mechanics

Helpers used by more than one frame. Roadmap §4 is the registry; the rule there is that **a helper
is born with its first consumer**, in its own sub-folder, with its own specs — and its interface is
frozen the moment that sub-project ships, recorded in roadmap §4 and in memory
`sixth-voice-build-state`. A later frame that needs more extends the helper in its own sub-project,
with every earlier spec still green.

The shape is usually the Draugr's: a static-function script plus whatever `.tres` it needs, no
autoload, no `class_name`. Every consumer reaches it by `preload`. **Armor is the one family that
isn't**: see its row below — two `Buff` subclasses (one `TO.STATBLOCK`, one `TO.RESIST_DAMAGE`)
parameterised by `@export`s on each consumer's own `.tres`, not a static-function script at all.

**Why no `class_name`**: global class names are registered from `project.godot`'s class list, which
is built at startup — so a `class_name` declared in a script a mod loads at runtime is never
registered, and cannot be referenced by that name at all. (This is a different problem from Godot
#83542, which is why a `class_name` script in the *base game* cannot be reliably script-extended;
that one is why the engine has so many autoloads. Both end at the same advice, for different
reasons.)

Built, and the interface frozen when its sub-project shipped — listed in the order they became
shared families, which is not the order of the frames: Armor's code was born at frame 2 and only
became a family at the Myconid.

| Terrain (difficult ground) | 6 Vauban, SP1 | **Four statics, all frozen:** `is_difficult(map, tile)` `is_unit_in_difficult(unit)` `is_entering_difficult(unit, next_anchor)` `lay(activation, specific, center, deployable)`, plus `PassiveGatedTerrainZone` with one `state_key` export. `lay` runs INLINE and hands the spawned unit back (the `Teleport.move` shape, not the Apocalypse Rail's queue-at-a-priority) — **or `null` when the spawn did not land** (a null or aborted spawn core, or a unit that never reached the map), so a caller must check the return before using it; `Unit.is_valid` is not that check, because it does not include `is_on_map`. **The unit it spawns is OWNED by `specific.unit`, and a deployable frame that must outlive its owner has to set `is_deactivated_on_owner_death = false` itself** — the export defaults to `true` and `EventService.remove_unit_from_game` kills owned markers that have it. **A consumer that wants "one field out at a time" must INTERSECT `deployed_ids` with the map**, the way `UnitAction.get_deployables_from` does (`unit_action.gd:537-545`) — never read the array for emptiness the way `action_jericho_deployable_cover.gd:5` does. `lay` records ownership before it spawns, so an aborted lay leaves the never-landed id behind; that residue is vanilla's own ordering (`action_system_deploy.gd:119` sets the owner, `:125` only then queues the spawn) and every vanilla deployable carries it. Not born: a lifetime for laid terrain, a Burst 2 frame, "damage in". | Leoleth, Shackleton |
| Lock-on consumed hook | 10 Naga, SP1 | **Five statics, all frozen when SP1 shipped (2026-09-22):** `was_consumed(context:Context) -> bool` (an `attack` context: `AttackRoll.check(object, &'consumed_lock')`; an `attack_declared` context: the target holds `buff_lock_consumed`), `consumer(context:Context) -> Unit` (`context.unit.get_attacker(context)` - an owned drone resolves to its owner), `is_lost(triggering:EventCore) -> bool` (a `statuses_changed` event whose `category_str` is LOCKON - the SAME virtual event carries the apply at PRE, so the caller reacts at POST), `apply(event, target:Unit, source_gear:GearCore) -> bool` (MANUAL, source = the gear's persistent id; false and no-op if already locked, if immune, or with an invalid gear), `source_of(unit:Unit) -> StringName` (the live status's source, empty if unlocked). **The Black Mountain needed none of this** (frame close finding M-6, correcting the note this replaces): its mark buff (`buff_dread_harbinger_mark`), `from_gear` = the Harbinger trait, IS the memory of whose lock it was - `Lockon.source_of` is never read. The mark gates on ANY Lock On loss on the holder (`Lockon.is_lost`, category only) and reads `buff_lock_consumed` in `activate` to tell a real consume from any other loss (ruling 9); a stacked SECOND Lock On from another source needs an extra guard (activate keeps the mark when the Harbinger's own gear still sources a live lock) so an unrelated clear cannot pay it out early. `spec/test_lockon.gd` pins all five signatures and fails on a sixth: an addition updates that pin in the sub-project that adds it. | Naga (the core passive, the core active, Ping, Binding Fangs), Black Mountain |
| Once-per-round on-hit | 2 Fitzgerald, `mt_knock_em_down`; extracted in close-out Pass D (2026-09-27) at the third instance | **Two statics, frozen:** `is_unspent(gear, usage_key) -> bool` (valid gear and `get_uses_this_round_alt(key) == 0`; an invalid gear reads SPENT) and `spend(attacker, target, gear_id, usage_key)` (on a valid CHARACTER target only, `increment_action_usage(key, false)`). The shape every consumer keeps: a `BuffWeaponTypeOnHit` subclass gates on `is_unspent(core.get_owner_gear(map), KEY)` after super, and its `OnHitEffect.should_abort` calls `spend` at `stage == apply_on` BEFORE super, because super rolls the save - so the round is spent by forcing the save, pass or fail (Fitzgerald ruling 15). Frame-specific gates (the Primrose's threat and overwatch tests) stay in the consumer, ahead of the helper. No `.tres` changed. `spec/test_once_per_round.gd` pins both signatures; mutating either half reddens every consumer's spec. | Fitzgerald (Knock 'Em Down), Maiden's Blush (Rend), Primrose (Magnetic Weight Redistribution; Wormhole Grasp, on the CORE Kit) |
| Character target (a drone takes a buff action) | close-out Pass F Task 11 (2026-09-27, author T14), born with three consumers | **One static, frozen:** `can_target_drone(action:ActionSystemApplyBuff, target:Unit, specific:SpecificAction) -> bool` - vanilla `ActionSystemApplyBuff.can_target_unit` (`action_system_apply_buff.gd:58-79`, 1.4.3) **minus its `is_actor()` line (:64)**, every other line copied verbatim with members read through `action`. **A COPY: diff it against vanilla after every modkit update.** The consumer shape: `can_target_unit` sends only `potential_target.is_drone()` here and everything else to `super`, so objects stay refused. A drone IS a character (Pass A). **Throw Magnets deliberately does not use it** (T14: a drone can never take the detach action). Lifetime on a drone (measured): an `until = END_OF_OWNERS_NEXT_TURN` buff ages only when its holder starts a turn, and a drone starts one only with its OWNER - so an owned drone's copy expires on time and an UNOWNED drone's never does on its own. Not the helper's job: a consumer with such a lifetime ages the copies itself - Reinforcement Blast's hidden `action_reinforcement_blast_age` reaction bumps `turn_count` at the Fitzgerald's turn start (Pass F T11b, author: "Clear it myself"). START_OF_OWNERS_TURN clears (Entrap) need nothing. `spec/test_character_target.gd` pins the signature and fails on a second method. | Fell the Mighty (Black Mountain), Entrap (Rakshasa), Reinforcement Blast (Fitzgerald's Grit Latch Magnets) |
